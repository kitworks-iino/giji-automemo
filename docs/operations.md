# 運用ガイド

## 最初の実機確認

本番会議の前に、同意済みの相手との短いテスト会議で両方の音声を確認してください。録音開始表示だけでは、正しい出力デバイスが選ばれていることまで確認できません。

1. Teamsのデバイス設定と、このアプリのマイク・再生デバイスを合わせる。
2. アプリ側で録音を開始し、自分と相手が交互に話す。
3. 録音を停止して、それぞれの音声を再生する。
4. モデルの準備後、文字起こしと話者ラベルを確認する。
5. 自動録音を有効にして、参加・退出による状態遷移を確認する。

録音停止後に会議一覧へ戻っても処理は続きます。次の会議は録音できますが、文字起こし・議事録生成はキューで順番に処理します。

## 状態の読み方

| 状態 | 意味 |
| --- | --- |
| 録音中 | マイクと再生デバイスの音を保存中 |
| 文字起こし中 | 保存した音声をローカルモデルで認識中。前の会議の処理待ちを含む |
| 話者分離中 | 相手側の音声を話者ラベルへ割当中 |
| 議事録生成中 | 設定したLLMへ文字起こしを送り、構造化された議事録を生成中 |
| 完了 | 処理が完了した状態 |
| エラー | 設定、音声、モデル、ネット接続などの確認が必要。途中の文字起こしは残る場合あり |
| 中断 | 前回のアプリ終了などで処理が止まった状態。保存済み音声から再処理可能 |

録音中にアプリを終了すると、保存できた音声を残して中断状態にします。次回起動時に黙ってLLMへ再送せず、ユーザーが再処理を実行します。強制終了やPC障害では最後の音声が欠けたりWAVが不完全になったりする可能性があるため、通常は停止操作を先に行ってください。

生成中に終了すると、実行中のモデル推論やAPI要求が戻るまでプロセスが残る場合があります。強制終了した処理は次回起動時に状態を確認して再処理してください。

## 自動終了と会議の延長

Teamsの参加状態は約2秒ごとに確認します。退出状態が標準で12秒間続くと録音を停止して処理を開始します。読み取り不能・検知不明の間は終了と判断しません。

- 予定時刻を超えても、参加中なら継続します。
- 予定より早く退出したら、その退出状態で停止します。
- 短い画面切替や再接続で退出状態が解消すると、終了の猶予をやり直します。
- 一度手動停止した同じ通話を直ちに自動録音し直すことはありません。退出の確認後、次の参加を待ちます。
- 長い切断や退出後の再参加は別セッションになる場合があります。
- 「自分が退出した」ことを終了と扱います。他の参加者全員が退出するまで待つものではありません。
- Teams上でのミュートはローカルマイク録音の停止とは異なります。録音したくない会話はアプリで停止してください。

会議一覧の件名とTeamsの参加状態の対応付けは完全ではありません。アプリから会議の参加操作をすると、その会議を優先します。同時刻に候補が複数あって特定できない場合は、特定の予定に決めつけず録音を保存します。

## 保存先とバックアップ

標準の保存先は `%LOCALAPPDATA%\giji-automemo` です。

```text
giji-automemo/
  giji.sqlite3          設定・会議・セッション・文字起こし・議事録
  recordings/
    <session-id>/
      microphone.wav   マイク音声
      system.wav       再生デバイスの音声
  models/              ダウンロード済みの音声モデル
```

Microsoft認証情報とLLM APIキーはWindowsの資格情報ストアに保存されます。SQLiteに平文で書く代替動作はしません。ストアが使用できない場合は、そのエラーを解消してください。

バックアップはアプリを終了してから保存先フォルダーをコピーします。別PCへコピーした場合、MicrosoftへのサインインとAPIキーの設定はやり直してください。音声と文字起こし自体は通常のローカルファイルであり、アプリが独自暗号化するものではありません。

セッションの削除は録音ファイルとその記録を削除します。録音中・処理中の削除はできません。モデルは複数セッションで共用します。手動でデータフォルダーを消す場合は、必要な議事録を先に書き出してください。

## よくある問題

| 症状 | 対応 |
| --- | --- |
| 相手の音量が0のまま | Teamsのスピーカー出力とアプリのループバック対象を一致させる。ヘッドセットの「通話」と「ステレオ」が別デバイスの場合にも注意 |
| 自分の音量が0のまま | Windowsのマイク許可、物理ミュート、選択したマイクを確認 |
| デバイス変更後にエラー | 保存済みの部分音声を確認。デバイスを再選択して新しく録音 |
| Teams状態が不明 | Teams会議ウィンドウを表示。改善しない場合は手動開始・停止。Teams更新で内部IDが変わる場合あり |
| 自動開始しない | 自動録音と録音確認を有効化。Teamsデスクトップ版か確認。状態が不明なら手動で録音 |
| 音声認識が遅い | 初回モデル取得と推論を区別する。CPU負荷を確認し、小さいモデルを選ぶ |
| 話者が混ざる | ヘッドセットを使用。別人が同じラベルになる場合や一人が複数ラベルになる場合があるため、音声と照合して名前を編集 |
| 誤った名前が議事録にある | 話者ラベルに実名を手動設定。担当者や期限は必ず原文と照合 |
| LLMがエラー | APIキー、ベースURL、モデルの利用権、利用限度、外部送信設定を確認して再処理 |
| モデル取得が失敗 | GitHub/Hugging Faceへの接続と空き容量を確認し、設定画面から再実行 |
| 接続URLの認証が切れた | 起動時に開いた画面を使う。アプリ再起動時には新しいトークン付き画面を開き直す |

APIキー・認証トークン・実際の文字起こしをGitHub Issueへ貼らないでください。問題の再現手順、Windows/Teamsバージョン、公開してよいエラーメッセージだけで報告できます。

キー未設定・外部送信OFFの場合も、ローカル文字起こしまでは保存されます。議事録生成段階のエラー案内を確認し、設定後に再処理してください。

## 毎日の起動

通常は `scripts\start.cmd` を起動します。必要ならWindowsのスタートアップフォルダーに、このファイルへのショートカットを自分で作成してください。初期状態でOSの自動起動設定は変更しません。アプリを使用しないときやPCがスリープ中は、予定同期と録音は実行されません。

## 起動オプション

```powershell
# デモデータを追加して起動
.\.venv\Scripts\python.exe -m giji --demo

# 保存先を変更
.\.venv\Scripts\python.exe -m giji --data-dir "D:\GijiData"

# 使用ポートを指定（標準は空いているポートを自動選択）
.\.venv\Scripts\python.exe -m giji --port 8765
```

同じ保存先を使うアプリを二重起動しないようロックします。通常起動をもう一度実行すると、稼働中のアプリの画面を開き直します。起動中は保存先の `launch-url.txt` に認証トークン付きURLを保持します。開発・診断用の `--no-browser` はブラウザーの自動起動を省略します。URLは自分のPCのブラウザーでのみ使用し、ファイル内容やURLを共有しないでください。ファイルは終了時に削除します。
